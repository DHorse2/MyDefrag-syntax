### Report Content Diagnosis

The human-readable report was reviewed as the primary evidence. It reported 15
locales, 8 components, zero validation errors or warnings, zero keyword
collisions, and 572 migration candidates.

The main finding was incomplete runtime integration rather than invalid language
data. English was complete, Mandarin contained 3 of 22 text entries and 3 of 20
keywords, and every other non-English locale contained no translations. Source
search found `createLanguageCatalog()` used only by its implementation and the
focused runtime test; extension, server, parser, preview, and diagnostic code did
not consume catalog keys. Several canonical texts remained present as raw
strings in runtime sources.

The 572-candidate inventory was also found to be materially inflated. The
scanner applies one regular expression to raw source text and performs only
minimal filtering. The report therefore includes debug messages, regular
expressions, globs, paths, npm commands, `use strict`, comments containing quote
characters, and the diagnostic-repair Markdown prompt alongside genuine
human-facing text. Genuine uncatalogued surfaces remain in package command
titles and settings, extension messages and pickers, parser diagnostics,
preprocessor output, and diagnostic-navigation UI.

The repository documentation confirms this boundary: Phase 1 was intentionally
additive and did not change extension, server, parser, preview, diagnostic, or
packaging behavior. No implementation change was made during this diagnosis.

### Missing Quoted-Text Diagnosis

The user clarified that generic `fr` must become `fr-CA` and that the migration
inventory must not suppress quoted text, even when this produces false
positives.

`package.json` line 3 contains `MyDefrag Script (.MyDc / .MyD)`. A focused probe
confirmed that the value matches the quote extractor, contains letters, is not
removed by the path/token filter, and is not removed by the `require(` filter.
It is removed later because it exactly equals the canonical
`extension.product.displayName` text. The final filter excludes every candidate
whose normalized text is already present in the canonical catalog.

Additional suppression points conflict with an exhaustive quoted-text
inventory: the regular expression requires at least four characters; strings
without letters are skipped; path-like single tokens are skipped; `require(`
strings are skipped; and each source file is truncated to 200 candidates. Thus,
removing only the canonical-text filter would not satisfy the clarified
requirement. No source change was made during this troubleshooting step.

### Authored Locale Catalog Clarification

The user asked whether `language/locales/en/catalog.json` is an aggregation and
where it comes from. Source tracing established that it is an authored locale
override file, not a generated aggregate. No repository script writes files
under `language/locales/<locale>`; `loadLocaleCatalogs()` reads `catalog.json`,
falls back to `catalog.sample.json`, or synthesizes an empty in-memory catalog.

The English file contains locale/status metadata, no component-text entry
overrides, and 20 approved semantic-keyword spellings keyed by canonical keyword
ID. Canonical English UI text comes from
`language/canonical/component-catalog.json`; canonical keyword identities and
spellings come from `language/canonical/semantic-keywords.json`.

Aggregation occurs only in `buildLanguageOutputs()`. It merges canonical data
with locale overrides, applies English fallback where needed, then writes
component catalogs and keyword maps beneath `build/language`. No source change
was made during this clarification.
